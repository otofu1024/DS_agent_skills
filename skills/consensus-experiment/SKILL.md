# 合意プロトコルの実験

頼まれたら、計画から実行、解析、報告までを進める。ユーザーは実験の経験が少ない前提で、各段階で何をなぜしたかを短く説明する。
方法の誤り（平均だけの報告、ウォームアップなし、1回だけの実行、故障なしの評価だけ）を、手順と道具で防ぐ。

## 原則

1. **既存の実装を優先する。** 自分で書くのは、使える実装がないときか、比べたい変更が既存の実装に入れられないときだけ
2. **まず再現する。** 新しい比較の前に、既存の実装で README や論文に近い結果が出るかを確かめる。環境の確認を兼ねる
3. **問いを1文で決めてから始める。**
4. **生データを残す。** 操作ごとの記録（開始時刻、レイテンシ、成否）を残し、集計だけで済ませない
5. **正しさも確かめる。** 性能だけを測らない
6. **結果に条件を付ける。** 実装と版、設定、環境、回数、負荷のかけ方

## 手順

### 1. 問いを決める

「〈何と何を〉〈どの条件で〉比べ、〈どの指標〉が〈どうなる〉かを確かめる」の形で書く。

- 指標: スループット、レイテンシの分布、故障からの回復時間、通信量など
- 主張したい範囲（LAN か WAN か、ノード数、故障モデル）と、用意できる環境で確かめられる範囲が合っているかを確かめる。合わなければ、範囲を狭めることを提案する

### 2. 既存の実装を探す

次の順に探す。

1. 論文のアーティファクト: academic-search スキルで論文を特定し、本文や要旨にあるリンク（GitHub、Zenodo）を探す
2. references/implementations.md の一覧（2026-10-31 時点の調査）
3. GitHub の検索: `curl -s "https://api.github.com/search/repositories?q=<protocol>+consensus&sort=stars&per_page=10"`

候補ごとに、ライセンス（ないものは改変・再配布しない）、最終更新、アーカイブ済みか、ベンチマークの仕組み、故障注入の仕組み、ビルドできるかを確かめる。使うコミットを記録する。

### 3. 環境を用意する

- **1台で行う**: レプリカを複数のプロセスとして起動する。ノードを分けたいときはネットワーク名前空間かコンテナを使う。遅延や分断は tc netem と iptables で入れる（references/methodology.md）
- **複数台で行う**: マシンの構成、ネットワーク、時計の同期を記録する
- Maelstrom はシミュレーションなので、プロトコルの振る舞いを素早く試すのに使う。実ネットワークの性能の主張には使わない
- ツールのインストールは、ユーザーに許可された範囲で行う。sudo が要る操作（tc、iptables、ip netns）は、何をするかを示してから実行する
- 注入した規則は実験の後に必ず消す。消すコマンドを記録に残す

### 4. 小さく動かす

- 最小の構成（crash 故障なら3ノード、Byzantine 故障なら4ノード）で、短時間だけ動かす
- README の例やベンチマークを、そのまま1回動かす
- 結果が README や論文から大きく外れたら、先に進まず原因を調べる（ビルドの設定、ログの出力、デバッグビルド、CPU の周波数）

### 5. 本番の計画を立てる

- 負荷: open-loop か closed-loop かを決めて明記する
- ウォームアップ、測定区間、繰り返しの回数（5回以上を目安にし、ばらつきを見て増やす）
- 変える変数は1つずつ（レプリカ数、バッチ、ペイロード、遅延、要求レート）。飽和点を探すときは要求レートを段階的に上げる
- 故障: リーダーの停止、分断、遅延・損失、遅いレプリカ。回復時間の終点を決める
- 保存先: `results/<実験名>/<条件>/run-<n>.csv`

長時間かかる実験と、sudo が要る実験は、計画を短く示してから始める。それ以外はそのまま進める。

### 6. 実行して記録する

1回ごとに、次を `results/<実験名>/<条件>/run-<n>.meta.md` に残す。

- 日時、実装と版（コミット）、ビルドの設定、実行したコマンド
- 環境（CPU、メモリ、カーネル、ネットワーク、注入した遅延や故障）

操作ごとの記録は CSV に残す。latstat が読む形式は、ヘッダつきで `start_us,latency_us,ok` の3列。実装のベンチマークが集計しか出さないときは、クライアント側で記録するように手を入れるか、その限界を報告に書く。

可能なら、操作の履歴を Porcupine などで検査し、linearizability などの主張する一貫性が保たれていたかを確かめる。

### 7. 解析する

latstat（リポジトリの tools/latstat）で集計する。

```bash
# 入れる（どちらか）
cargo install --git https://github.com/otofu1024/DS_agent_skills latstat
cargo install --path tools/latstat

# 各回の統計と、回をまたいだ 95% 信頼区間（最初の10秒をウォームアップとして除く）
latstat results/exp1/n3/run-*.csv --warmup 10

# 機械可読の出力と、CDF を描くためのデータ
latstat results/exp1/n3/run-*.csv --warmup 10 --json > results/exp1/n3/summary.json
latstat results/exp1/n3/run-*.csv --warmup 10 --cdf results/exp1/n3/cdf.csv
```

- 平均だけでなく、p50・p99・p99.9 と CDF を示す
- 回をまたいだ信頼区間が重なる差を、「速い」「遅い」と言わない
- グラフは、スループットとレイテンシの曲線、レイテンシの CDF、故障を入れたときのスループットの時系列を基本にする

### 8. 報告する

1. 問い（手順1）
2. 条件（実装と版、設定、環境、回数、負荷のかけ方、注入した故障）
3. 結果（表とグラフ。信頼区間つき）
4. 解釈と限界（確かめられなかった範囲、システムモデルとの違い）
5. 再現の手順（コマンドとファイルの場所）

ユーザーが直接読む最終稿は、yomiyasu スキルが使えるなら推敲する。数値、コマンド、専門用語は変えない。

## 自分で実装するとき

- 既存の実装を土台にし、比べたい変更だけを入れる。ゼロから書かない
- 新しく書くプログラムは Rust を第一候補にする（作者の好み）。既存の実装が別の言語なら、その言語に合わせる
- 変更の前後を同じ環境・同じ設定で測る
- safety に関わる変更なら、実験の前に TLA+ などで小さな構成のモデル検査を検討する
