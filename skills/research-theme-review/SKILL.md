# 研究テーマの批評と選別

ユーザーが出したテーマ案を、すぐには肯定しない。調べてから、基準に照らして判定する。
目的は反対することではなく、本当に価値のあるテーマだけを残すことにある。基準を満たしたテーマには、はっきり「採用」と言う。

## 姿勢のルール

1. **調べる前に評価しない。** 最初の返答で「面白い」「良いですね」と言わない
2. **反論には根拠を付ける。** 根拠は、確認済みの論文（ID つき）、条件つきの既知の定理、論理のいずれか
3. **反論ごとに撤回の条件を書く。** 「何が示されれば、この指摘を取り下げるか」
4. **成立させる道も示す。** モデルを変える、問題を絞る、別の検証方法を使う、など
5. **基準を満たしたら採用と言う。** 迎合も、反対のための反対も、どちらも役に立たない
6. **言い返されただけでは判定を変えない。** ユーザーが反論してきたら、新しい根拠があるかを見る。あれば判定を変え、なければ理由を添えて維持する

## 手順

### 1. 案を一文にする

「〈どのモデルで〉〈何の問題に対して〉〈何をすると〉〈何が良くなる・何が示せる〉」の形に言い換える。
言い換えられない部分が、最初の論点になる。曖昧な点は推測で埋めて進み、推測したことを明記する。判定を左右する点だけを、最後にユーザーへの問いとして返す。

### 2. システムモデルを仮に決める

system-model-spec スキルでモデルカードを作る。テーマ案の段階では未記載の項目が多いのが普通。結論を左右する項目（タイミング、故障、閾値、暗号の仮定、解く問題）だけは仮に決め、仮に決めたことを書く。

### 3. 先行研究を探す

academic-search スキル（Semantic Scholar）で探す。最低限、次を行う。

- 同じ問題を言い換えたクエリを3つ以上使う。分野ごとの呼び名を含める（field-positioning スキルの用語の対応を使う）
- 最も近い論文が見つかったら、`get_citations` で後続研究を、`get_references` で先行研究をたどる
- 直近の論文を `year`（例: 直近3年）で絞って確かめる
- 隣接分野（理論、システム、ブロックチェーン、DB、形式検証）を少なくとも1つ確かめる。分野をまたいだ比較は field-positioning スキルで行い、主に向ける分野を決める

最も近い先行研究を3〜5本選び、ID つきで並べる。見つからなかった場合も使ったクエリを記録する。「見つからない」は「存在しない」と同じではない。

### 4. 差分を明確にする

最も近い先行研究ごとに、4つの軸で同じか違うかを書く。

| 軸 | 問うこと |
| --- | --- |
| モデル | タイミング、故障、閾値、暗号、敵対者は同じか |
| 問題 | 同じ問題か。validity や liveness の条件は同じか |
| 手法 | 技法は新しいか。別の分野で既に使われていないか |
| 結果 | 定理は強くなったか。性能はどの条件で、何に対して良くなったか |

差分がモデルだけ（同じことを少し違う仮定で行う）のときは、その仮定の違いに意味があるかを問う。現実の配備で効くのか、理論的な難しさが変わるのか。

### 5. 基準で評価する

references/rubric.md の6つの基準それぞれについて、評価（強い・弱い・不明）と根拠を書く。

1. 新規性
2. 重要性
3. モデルの妥当性
4. 既知の結果との整合
5. 検証可能性
6. 実現可能性

理論の研究なら証明の筋道を、システムの研究なら評価計画を、5の中で具体的に書く。どちらの場合も「どうやって示すのか」が言えないテーマは採用しない。

### 6. 判定する

次の順に当てはめ、最初に当たったものを判定にする。

| 順 | 判定 | 条件 |
| --- | --- | --- |
| 1 | 棄却 | 新規性か既知の結果との整合が「弱い」で、直す道がない。例: 同じモデル・同じ問題で同等以上の結果が既にある。既知の不可能性と矛盾し、仮定の違いで説明できない。重要性を示せる見込みがない |
| 2 | 保留 | 判定を左右する基準が「不明」で、何を調べれば決まるかが分かっている |
| 3 | 改訂 | 「弱い」の基準か、致命的・重要な指摘があるが、直し方が見えていて、直せば採用の条件を満たす道筋がある |
| 4 | 採用 | 新規性と既知の結果との整合が「強い」。重要性、モデルの妥当性、検証可能性、実現可能性に「弱い」がない。致命的な指摘がない |

- 採用のときに「不明」の基準が残るなら、それが判定を変えない理由を書く。書けなければ保留にする
- 判定は1つに決める。「どちらとも言える」で終わらせない
- 棄却する場合も、救える部分（別の問題への転用、モデルの変更）があれば書く

### 7. 台帳に記録する

作業ディレクトリの `research-themes/` に、テーマごとに1ファイル（`YYYY-MM-DD-<短い英語名>.md`）で残す。形式は assets/theme-record.md に従う。

- 判定が変わったら上書きせず、履歴に追記する
- 棄却したテーマも消さない。駄目だった理由は、次のテーマ作りの材料になる
- 未発表のアイデアなので、公開リポジトリには置かない。作業ディレクトリがこのスキル集のリポジトリ（DS_agent_skills）の中か、公開されている remote がありそうな git リポジトリの中なら、作る前に置き場所をユーザーに確かめる

### 8. ユーザーに返す

次の順で、短くまとめる。

1. 判定（1行）
2. 理由の要点。重い指摘から3つまで、それぞれ撤回の条件つき
3. 最も近い先行研究（ID つき）と、それぞれとの差分
4. 次にやること。改訂なら直し方、保留なら調べること、採用なら最初の一歩
5. 判定を変えうる問い（ユーザーにしか答えられないもの）

ユーザーが直接読む最終稿なので、yomiyasu スキルが使えるなら推敲する。判定、引用、専門用語、数式は変えない。

## 依頼の種類ごとの進め方

- **「こういう研究ないかな」**: まず手順3で探し、見つかったものを報告する。そのうえで、ユーザーが変種を追いたいなら、その変種をテーマ案として手順1から評価する
- **複数案の比較**: 各案について手順1〜6を短く行い、比較表を作る。1つを推し、他の案が劣る理由を書く
- **以前のテーマの見直し**: 台帳を読み、前回の検索以降の論文を `year` で絞って探し直す。判定が変われば履歴に追記する

## よくある弱点

分散合意のテーマで繰り返し現れる弱点の型と、その確かめ方を references/critique-patterns.md にまとめてある。手順4〜5で必ず照らし合わせる。
