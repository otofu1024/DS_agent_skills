# 隣接分野との位置づけ

分散合意は、理論、システム、ブロックチェーン・暗号、データベース、形式検証の各分野が、別々の言葉と前提で研究している。
ある分野で新しく見えることが、別の分野では古典的な結果であることも多い。逆に、別の分野の結果がそのまま当てはまらないこともある。
このスキルでは、対象の論文やテーマを各分野の見方で並べ、何が本当に違うのかをはっきりさせる。

## いつ使うか

- 論文やテーマの「関連研究」を、分野をまたいで洗い出したいとき
- 「ブロックチェーンの BFT と古典的な BFT は何が違うのか」のような比較
- テーマをどの分野の読者に向けるかを決めるとき（research-theme-review の途中で使う）
- 論文が別分野の先行研究を見落としていないかを確かめるとき（consensus-paper-critique の途中で使う）

## 手順

### 1. 対象の核を取り出す

次の3つを1行ずつ書く。

- 問題: 何に合意するのか（system-model-spec スキルの手順3で特定した問題）
- モデル: 結論を左右する仮定（タイミング、故障と閾値、暗号、敵対者）
- 貢献の種類: 定理（可能性・不可能性・下界）、プロトコル、実装と評価、検証手法

### 2. 分野ごとの言葉に言い換える

references/fields.md の「用語の対応」を使い、対象を各分野の言葉で言い換える。言い換えたものをクエリにして、academic-search スキルで分野ごとに検索する。各分野で最も近い研究を1〜3本選び、ID を付ける。

分野ごとの結果は、次の3つを区別して記録する。

- 見つかった: 最も近い研究（ID つき）
- 見つからなかった: 使ったクエリを書く。「見つからない」は「存在しない」と同じではない
- 対象外: 対象の問題やモデルとその分野の前提が違い、比べても意味がない（crash 故障だけの SMR を、Byzantine 故障を前提にするブロックチェーンの合意と比べる、など）。理由を書く。ただし、違いそのものが位置づけの材料になるときは、手順4で触れる

### 3. 分野ごとの扱いを比べる

分野ごとに次の4点を書いて表にする。

| 観点 | 問うこと |
| --- | --- |
| 前提 | その分野では、どのモデルが普通か。対象の仮定は強いか弱いか |
| 新規性の基準 | その分野では何が新しいとみなされるか |
| 証拠の形 | 定理と証明か、実装と評価か、機械的な検証か |
| 既存の到達点 | 最も近い研究は何を示しているか |

### 4. 差分を言葉にする

次の問いに答える。

- 対象の結果は、別の分野の既知の結果から導けないか（再発見ではないか）
- 別の分野の結果（特に下界や不可能性）は、対象のモデルにそのまま当てはまるか。当てはまらないなら、どの仮定のせいか
- 用語のずれで、比較が食い違っていないか（例: finality と decision、view と term と round）
- 別の分野の手法（証明の技法、実装の工夫、検証の道具）で、対象の問題をもっと簡単に扱えないか

### 5. 出力する

1. 位置づけの要約（2〜3文）。「〈分野X〉の〈結果Y〉に対して、〈仮定Z〉を変えた点が新しい」の形を目安にする
2. 分野ごとの比較表（手順3）
3. 見落とされている可能性のある研究（ID つき）
4. 用語の対応（対象で使われる語と、各分野での呼び名）
5. 主に向ける分野の推奨と、その分野の読者が求める証拠
6. 参考文献と検索の記録（使ったクエリ、分野ごとの「見つかった・見つからなかった・対象外」）

ユーザーが直接読む最終稿は、yomiyasu スキルが使えるなら推敲する。他のスキルへ途中結果として渡すときは推敲しない。

## 注意

- 分野の特徴は傾向にすぎない。理論の会議にも実装を伴う論文はあり、システムの会議にも証明を伴う論文はある。個々の論文は中身で判断する
- 「別の分野ですでに知られている」と書くときは、その研究を ID つきで挙げる。挙げられないなら、そうは書かない
