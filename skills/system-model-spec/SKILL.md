# システムモデルの明確化

分散合意の議論は、システムモデルが1つ違うだけで結論が変わる。同じ「合意」でも、非同期か部分同期か、crash か Byzantine か、署名があるかないかで、解けるかどうかも必要なノード数も変わる。
このスキルでは、論文や研究テーマのモデルを項目ごとに洗い出し、書かれていない仮定と、既知の不可能性・下界との関係をはっきりさせる。

## いつ使うか

- 論文を読んで前提を整理したいとき
- 自分のテーマ案の前提を固めるとき（research-theme-review の途中で使う）
- 「このプロトコルは何個の故障に耐えるのか」「この主張は FLP と矛盾しないか」といった問い
- 2本の論文を比べるとき。モデルを揃えずに性能や閾値を比べると誤る

## 手順

### 1. 材料を読む

- **論文**: モデルを述べた節（"System Model"、"Model and Definitions"、"Preliminaries"）、問題の定義、主定理、証明で使う補題、評価の設定を読む。モデルの節だけでは足りない。仮定は証明や評価の中に紛れていることが多い
- **テーマ案**: ユーザーの説明から読み取れる範囲で埋める。足りない項目は「未記載」のままにして、結論を左右する項目だけを手順5で問いとして返す

### 2. モデルカードを埋める

assets/model-card.md の形式で、各項目に次の3つを書く。項目の定義と見落としやすい点は references/model-dimensions.md にある。

- **値**: 例「部分同期。GST は未知、GST 後の遅延上限 Δ は既知」
- **出典**: 論文の節やページ、定理番号。テーマ案なら「ユーザーの説明」
- **状態**: 明示（本文に書いてある）／暗黙（証明や評価から推測した。根拠を書く）／未記載（要るはずの仮定が書かれていない）／対象外（その問題やモデルでは考えなくてよい。理由を書く）

「未記載」と「対象外」を区別する。crash 故障だけのモデルで署名や敵対者の強さが書かれていないのは「対象外」で、欠点ではない。
1つの項目に複数の事実が入るときは、事実ごとに状態を書く（例: 通信路は「メッセージの損失と順序の入れ替えを許す（明示）」「送信者の認証（未記載）」）。
safety と liveness で使う仮定が違うのは普通なので、タイミングの項目は分けて書く。

### 3. 問題と性質を書き下す

解いている問題を1つに特定する。似た名前の別の問題が多い。

- consensus（全員が入力を持ち、1つの値に合意する）
- Byzantine broadcast（1人の送信者の値に合意する）
- state machine replication（SMR）/ atomic broadcast（コマンド列の順序に合意し続ける）
- atomic commit（全員がコミットに賛成したときだけコミットする）
- レジスタの模倣（read/write。合意より弱い問題）

次に、性質を safety と liveness に分けて、論文の言葉で書く。validity は種類が多い（strong、weak、external など）ので、どれなのかを特定する。liveness は「いつ」成り立つのか（GST 後、正しいリーダーのとき、確率1で、など）まで書く。

### 4. 既知の結果と照らし合わせる

references/known-results.md の表と照らし合わせる。

- 主張が不可能性や下界を「破っている」ように見えたら、どの仮定が違うのかを特定する。違いを説明できなければ、主張か自分の読みのどちらかが誤っている。どちらなのかを詰める
- n と f の関係が、モデルから決まる下限と合っているかを確かめる
- 表にない結果を根拠に使うときは、academic-search スキルで原典を確かめてから使う

### 5. 指摘をまとめる

重大度を付けて並べる。

| 重大度 | 例 |
| --- | --- |
| 致命的 | モデルが不明確で主張の真偽が決まらない。既知の不可能性と矛盾し、仮定の違いで説明できない |
| 重要 | 現実の配備で成り立たない強い仮定。暗黙の仮定が証明に効いている。比較相手とモデルが揃っていない |
| 軽微 | 用語の不統一。他分野の用語とのずれ |

各指摘には、確認すべき箇所（論文の節、著者に聞くべき点、ユーザーに決めてもらう点）を付ける。

### 6. 出力する

単独で使うときは、次の順で書く。他のスキル（consensus-paper-critique など）の途中で使うときは、呼び出したスキルの出力の順に従い、その中に入れる。

1. モデルカード
2. 問題と性質の定義
3. 既知の結果との関係（矛盾がない理由、または矛盾の疑い）
4. 指摘の一覧（重大度順）
5. 未記載のまま残った項目と、それを決めるための問い

## 判断のコツ

- 「非同期」と書いてあっても、liveness の証明で GST やタイムアウトを使っていれば、liveness については部分同期のモデルになっている
- 「Byzantine 故障に耐える」とあっても、署名（PKI）の有無、敵対者が静的か適応的か、配送順を敵対者が決められるかで意味が変わる
- n ≥ 3f+1 のような閾値は、タイミング・故障・問題の組み合わせで決まる。閾値だけを取り出して比べない
- 「最適なレイテンシ」「線形の通信量」などの主張では、何を数えたのか（ラウンド数、メッセージ遅延、メッセージ数、ビット数、署名の数）と、どの場合の値なのか（故障なし、リーダーが正しい、GST 後、最悪の場合）を確かめる
- 分野によって同じ言葉の意味が違う。ブロックチェーンの "finality" と合意の decision、DB の "consensus" と分散計算の consensus、linearizability と serializability は特に混ざりやすい
- 書かれていないことを補うときは、必ず「暗黙」と明記し、推測の根拠を書く

## 他のスキルとの関係

- 文献の確認には academic-search スキルを使う
- research-theme-review に結果を渡すときは、モデルカードと指摘をそのまま渡す（推敲しない）
- ユーザーが直接読む最終稿は、yomiyasu スキルが使えるなら推敲する。用語、数式、閾値、引用は変えない
