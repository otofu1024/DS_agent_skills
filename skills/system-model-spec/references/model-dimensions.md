# モデルの項目と見落としやすい点

モデルカードの各項目について、取りうる値と、論文で省かれやすい点をまとめる。

## 1. 通信

| 値 | 意味 |
| --- | --- |
| メッセージ通信 | プロセス間でメッセージを送り合う。合意の研究のほとんど |
| 共有メモリ | 共有レジスタなどのオブジェクトを読み書きする |

確認すること:

- 通信路の信頼性: reliable（失われない、重複しない、作られない）か、fair-lossy（無限回送れば届く）か。再送を誰がするのか
- 送信者の認証: 受信者が送信者を識別できるか（authenticated channels）。署名とは別の仮定で、ほとんどの論文が暗黙に置いている
- 全員が全員と直接つながっているか。gossip や部分的なトポロジーを使うなら明示されているか
- FIFO を仮定しているか

## 2. タイミング

| 値 | 意味 |
| --- | --- |
| 同期 | メッセージ遅延とプロセスの処理速度に既知の上限がある。ラウンド単位で進むと考えてよい |
| 非同期 | 上限がない。配送順も敵対者（スケジューラ）が決める |
| 部分同期（DLS 版1） | 上限は存在するが、値は分からない |
| 部分同期（DLS 版2） | 上限は分かっているが、成り立つのは未知の時刻 GST 以降 |

確認すること:

- safety と liveness で使うタイミングの仮定を分けて書いているか。多くのプロトコルは、safety は非同期でも保ち、liveness に部分同期を使う
- GST 前に送られたメッセージの扱い（GST + Δ までに届く、など）
- 時計の仮定: 同期した時計、ずれ（drift）の上限。リースや leader lease による読み取りは、時計の仮定に依存する
- responsiveness: 実際の遅延 δ に比例して進むのか、上限 Δ を待つのか
- 評価で使う「タイムアウト」の値が、モデルのどの仮定に対応するか

## 3. 故障

| 値 | 意味 |
| --- | --- |
| crash-stop | 止まったら二度と動かない |
| crash-recovery | 止まった後に復帰する。安定記憶（disk）に何が残るかが重要 |
| omission | 送信や受信を取りこぼす |
| Byzantine | 任意の振る舞い。嘘、二枚舌、沈黙を含む |
| hybrid | 種類の違う故障が混在する。信頼できる部品（TEE、信頼できるカウンタ）を仮定するものもある |

確認すること:

- f は「最大の故障数」か「割合」か。重み付き（stake）なら重みの定義
- crash-recovery で、復帰したプロセスが状態を失う（amnesia）ことを許すか。fsync を前提にしていないか
- 故障したプロセスと遅いプロセスを区別できないこと（非同期・部分同期）を考慮しているか
- クライアントの故障・悪意を考えているか

## 4. 閾値と quorum

- n と f の関係（n ≥ 2f+1、n ≥ 3f+1 など）と、quorum の大きさ
- quorum の交差の論理: どの2つの quorum が、正しいプロセスを何個共有する必要があるか
- Flexible Paxos のように、段階ごとに quorum の大きさを変えていないか
- fast path がある場合、fast path の quorum と、それが成り立つ条件

## 5. 暗号と準備

| 値 | 意味 |
| --- | --- |
| 暗号なし | 口頭メッセージ（oral messages）のモデル |
| 署名・PKI | 偽造できない署名。理想化して扱うことが多い |
| 閾値署名 | 準備（信頼できる dealer か DKG）が要る |
| 共通の乱数 | common coin、random beacon、VRF |

確認すること:

- 準備（setup）の仮定: PKI がいつ・誰によって作られるか。信頼できる dealer を置いていないか
- 計算量的な仮定か、情報理論的か
- 通信量の比較で、署名の大きさや検証のコストを数えているか

## 6. 敵対者

| 値 | 意味 |
| --- | --- |
| 静的 | 実行の前に、どのプロセスを乗っ取るかを決める |
| 適応的 | 実行の途中で、見た情報をもとに乗っ取るプロセスを決める |
| 強く適応的 | 乗っ取ったプロセスが送信済みのメッセージを取り消せる（after-the-fact removal） |

確認すること:

- 配送順を敵対者が決められるか（非同期では普通は決められる）
- 計算能力の上限（多項式時間など）
- 乗っ取る対象が時間とともに移る（mobile）か

## 7. 参加者

- 参加者の集合は固定で全員が知っているか（permissioned）。参加者数 n を全員が知っているか
- 再構成（membership change）を扱うか。扱わないなら、その限界を書いているか
- permissionless（Sybil 対策に proof-of-work や proof-of-stake を使う）か

## 8. 決定性と乱数

- 決定的か乱択か。乱択なら、終了は確率1か、期待ラウンド数はいくつか
- 乱数は各自のもの（local coin）か、全員共通（common coin）か

## 9. 問題

| 問題 | 要点 |
| --- | --- |
| consensus | 全員が入力を持ち、1つの値に合意する |
| Byzantine broadcast | 1人の送信者の値に合意する。送信者が悪意を持つこともある |
| interactive consistency | 全員の入力のベクトルに合意する |
| SMR / atomic broadcast | コマンドの全順序に合意し続ける。クラッシュ故障の非同期モデルでは consensus と互いに帰着できる |
| atomic commit | 全員が賛成したときだけコミットする。consensus とは validity が違う |
| レジスタの模倣 | linearizable な read/write。f < n/2 なら合意なしで実装できる |

validity の種類（どれかを特定する）:

- strong validity: 正しいプロセスの入力が全員同じなら、その値に決まる
- weak validity: 故障がなく全員の入力が同じなら、その値に決まる
- external validity: 決まる値が、外部から与えられた述語を満たす（ブロックチェーンの BFT でよく使う）

## 10. 性質

- safety: agreement（2つの正しいプロセスが違う値に決めない）、validity、integrity（一度しか決めない）、全順序
- liveness: termination の条件（GST 後、正しいリーダーのとき、確率1、など）
- クライアントから見た一貫性: linearizability、読み取りの扱い
- 公平性: 検閲耐性、リーダーによる並べ替えの制限

## 11. 計量

- 何を数えるか: ラウンド数、メッセージ遅延の段数、メッセージ数、ビット数、署名や authenticator の数、計算量、記憶量
- どの場合か: 故障なし、リーダーが正しい（good case）、最悪の場合、GST 後、view change の間
- 実装評価なら: バッチの大きさ、ペイロードの大きさ、レプリカ数、ネットワーク（LAN か WAN か）、クライアントの数と負荷のかけ方

## 12. 配備と実装

- 永続化（fsync の有無）、メモリ上だけの評価になっていないか
- 時計とタイムアウトの設定
- クライアントの扱い（重複リクエスト、再送、読み取り）
- 評価環境がモデルの仮定と合っているか（例: 非同期を主張しつつ、評価は LAN の安定したネットワークだけ）
