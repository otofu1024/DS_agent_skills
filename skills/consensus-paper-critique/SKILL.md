# 合意プロトコルの論文の批判的な読解

論文が「主張していること」と「実際に示していること」を分けて読む。
要約で終わらせない。各主張について、どんな根拠があり、どの条件で成り立ち、どこが弱いのかを書く。
批判は公平に行う。まず貢献を最も強い形で読み取り（steelman）、それから弱点を探す。

## 手順

### 1. 本文を手に入れる

- PDF を渡されたら、それを読む
- ID（DOI、arXiv ID、題名）を渡されたら、academic-search スキルの `get_paper` で書誌情報と `openAccessPdf` を取り、公開されている本文を読む
- 本文が手に入らないときは、要旨と書誌情報だけで分かる範囲に限って評価し、その限界を最初に書く

### 2. 貢献を主張の形で書き出す

序論の貢献リストや要旨から、主張を1つずつ書き出す。各主張には適用範囲を付ける。

例: 「部分同期・n ≥ 3f+1・署名ありのモデルで、リーダーが正しい場合のコミットまでのレイテンシが3メッセージ遅延になる」

範囲が書かれていない主張（「高速」「スケーラブル」「実用的」）は、範囲が不明であること自体を指摘する。
「理解しやすい」「使いやすい」のような人についての主張は、何で測ったか（理解度のテスト、実装の正しさ、作業時間）と、誰を対象にしたかを範囲として書く。

### 3. 主張と根拠を対応づける

主張ごとに、根拠の種類、場所、強さを表にする。

| 主張 | 根拠の種類 | 場所 | 強さ |
| --- | --- | --- | --- |
| | 定理と証明 / モデル検査 / 実験 / 引用 / なし | 節・定理番号・図 | 十分 / 部分的 / 不十分 |

- 要旨や序論にあるのに、本文に根拠がない主張を探す
- 根拠が主張より狭い場合（4ノードの実験だけで「スケーラブル」と言う）を探す

### 4. システムモデルを明確にする

system-model-spec スキルでモデルカードを作る。特に、証明や評価で使われているのにモデルの節に書かれていない仮定を探す。
モデルカードは、手順9の「5. 隠れた仮定」の中に入れる。

### 5. 証明を読む（理論の主張がある場合）

- 問題の定義（validity、liveness の条件）が、主張している問題と一致しているか
- 各補題が、どの仮定を使っているか。使われていない仮定、使っているのに書かれていない仮定はないか
- 境界の場合が扱われているか: view change の途中、GST の前後、Byzantine な参加者の equivocation、crash-recovery の後、quorum がちょうど交わる場合。論文のモデルに当てはまらない場合（crash 故障だけのモデルでの equivocation など）は「対象外」と書き、論文のモデルにある境界の場合に絞る
- 下界や不可能性を「破った」主張なら、どの仮定の違いで説明できるか（system-model-spec の既知の結果と照らす）

証明の正しさについての自分の判断の確信度を書く。細部に疑いが残るときは、小さな n と f での tla-plus-model-check スキルによるモデル検査か、lean-consensus-proof スキルによる機械的な証明を提案する。読んだだけで「正しい」と断言しない。

### 6. 評価を読む（実装と実験がある場合）

references/evaluation-checklist.md の項目で確かめる。評価が性能の測定でない場合（人を対象にした実験など）は、チェックリストの該当する節を使う。論文の評価に当てはまらない項目は「対象外」と書き、欠点に数えない。性能の測定なら、少なくとも次の点を見る。

- ベースライン: 何と比べたか。版と設定は公平か
- 負荷: クライアントの数と負荷のかけ方。レイテンシの測り方
- 指標: 平均だけでなく分布（パーセンタイル）を示しているか
- 故障: 故障を入れた評価があるか。リーダーの停止と回復時間を測っているか
- 環境: LAN か WAN か。ノード数の範囲。主張の範囲と合っているか
- 再現性: 繰り返しの回数とばらつき。アーティファクトの公開

### 7. 先行研究との関係を確かめる

academic-search スキルで次を行う。

- `get_references` で、この論文が何を引用しているかを見る
- 最も近い先行研究を別に検索し、引用されていないものがないかを確かめる
- `get_citations` で後続研究を見て、この論文の結果を改良・反証・修正した研究がないかを確かめる。`intents` が result や methodology の引用と、`isInfluential` な引用を優先して読む

### 8. 隣接分野から見た位置づけを確かめる

field-positioning スキルで、他の分野から見て新しいのか、古典的な結果の言い換えではないのかを確かめる。

### 9. まとめる

次の順で書く。

1. 書誌情報（ID つき）
2. 要約（1段落）。何を、どのモデルで、どう示したか
3. 貢献ごとの評価（手順3の表）
4. 主な弱点（重大度順）。各弱点に根拠と、「何が示されれば取り下げるか」を付ける
5. 隠れた仮定（手順4）
6. 位置づけ。最も近い先行研究との差分と、他分野から見た違い
7. 次に確かめること。著者の他の論文、アーティファクト、後続研究
8. 研究の種になりそうな点。弱点や未解決の点から派生するテーマ候補。追うなら research-theme-review スキルで評価する
9. 参考文献と検索の記録。引用した文献（ID つき）、使ったクエリ、使えなかった検索とその理由（429 で引用関係を取れなかった、など）

ユーザーが直接読む最終稿は、yomiyasu スキルが使えるなら推敲する。引用、数式、専門用語、評価は変えない。

ユーザーが保存を頼んだら、作業ディレクトリの `paper-notes/<第一著者の姓><年>-<短い英語名>.md` に保存する。

## 注意

- 論文に書いてあることと、自分の推測を混ぜない。推測には「推測」と書く
- 弱点の指摘は具体的に書く。「評価が不十分」ではなく、「故障を入れた評価がなく、リーダー停止時の回復時間が分からない（6節）」と書く
- 良い点も書く。弱点だけを並べると、論文の価値の判断を誤る
